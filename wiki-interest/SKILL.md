# wiki-interest

Ви — агент, який керує навичкою. Використовуйте наявний CLI; навичка сама не викликає LLM. Не пишіть альтернативний аналітичний код і не рахуйте показники самостійно. Можна створювати вхідні JSON-файли. Пояснення — українською; звіт типово `uk`, `en`/`ru` — лише за явним вибором.

## Підготовка

Визначте `WIKI_INTEREST_ROOT` як директорію **цього завантаженого SKILL.md**, а не поточний проєкт. У shell використовуйте `npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- ...`. Усі шляхи беріть у лапки. Відносний `--input` розв’язується від кореня навички; для файлу в проєкті користувача передавайте абсолютний шлях. Runtime і ресурси визначає код від власного фізичного розташування, включно з symlink.

Для нового середовища виконайте `npm --prefix "$WIKI_INTEREST_ROOT" run --silent doctor`. Це перевірка, а не інсталятор. Встановлення й дозволи описані в [підключенні](references/installation.md). Після налаштування не повторюйте встановлення для кожного запиту. Ніколи не запускайте `npx` для прихованого завантаження пакетів.

## Завершення в межах одного запиту

Спершу забезпечте [докази відповідників](references/sources.md). `resolve` зберігає URL з info, фактичний QID, поточну revision і зміст. Прочитайте з resolution лише вступ, уточнення й релевантні розділи кандидатів. Зафіксуйте рішення операцією `review`: exact / broader / narrower / section_only / mention_only / ambiguous, предмет, контекст, причина, дослівний evidenceQuote із збереженої версії. Новий resolutionId передайте в concepts або sourceResolutionIds. Це робота агента в цьому самому запиті; окремий промпт користувача не потрібний, якщо тема вже визначена. Технічне confirmed не означає змістового exact; pending не приховуйте.

Для topic також використовуйте `analysis.sourceResolutionIds` з reviewed resolution обраних концепцій. Для auto-supplement перевірте зміст реально доданих мов; metadata-каталог інших мов не є аналізом. Не включайте broader/narrower/section_only/mention_only у точне порівняння. Для розділу беріть sectionUrl з коду й прямо кажіть, що перегляди всієї сторінки не є переглядами розділу. Інший QID не зливайте через схоже слово чи назву.

Після змістовного вибору QID або зафіксованого topic plan використовуйте `research`. Поле `analysis` містить звичайний JSON analyze; `report` — налаштування PDF. Код перевіряє мовні відповідники, застосовує мовну політику, збирає дані, розраховує доступні показники та запускає report. Окремі операції нижче зберігаються; виконуйте їх у межах цього самого запиту, якщо потрібен розгорнутий workflow.

Типово `languagePolicy: auto-supplement`, порядок `supplementalPriority: ["uk","en","de","fr"]`, не більше двох додаткових мов. «Лише ці мови» завжди означає `strict`. Додаткові мови обирає код за тією самою концепцією й придатною історією, без оцінювання знака зростання. Не просіть окреме погодження на кожну додаткову мову. Якщо всі запитані мови придатні, дослідження не розширюється.

URL статті передавайте в `resolve.articleUrl` замість query/qid. Код перевіряє канонічну сторінку, redirects, wikibase_item та Wikidata. При відсутньому sitelink запускає обмежений локальний пошук. Не перекладайте заголовки й не підміняйте концепцію. Стани confirmed / not_found / incomplete / ambiguous різні; мовний зв’язок не гарантує однакового змісту статей.

Одна відсутня стаття або кілька дат не є приводом завершувати відповідь словами «можу продовжити». Завершіть доступні гілки й PDF зараз. Для прогалин читайте `entries[].recovery`, `findings[].method`: daily, api_monthly, matched_calendar_change, unavailable. Останній — зміна лише на зіставних днях, не точне зростання повного року. Не рахуйте альтернативу вручну, не заповнюйте null нулями. [Точні правила й пороги](references/completion.md).

Відповідь має окремі блоки **«Результат для запитаних мов»** та **«Додаткове порівняння»**, таблицю доступних показників, метод/покриття, суперечності, недоступні мови й шлях до PDF з artifacts. Читайте executionStatus, requestCompletion, metricQuality; успіх PDF не доводить повноти початкового порівняння. Не вибирайте один зручний finding замість усіх суттєвих застережень.

Перед метриками завжди дайте таблицю **Мова | Стаття з прямим посиланням | Тип відповідності | Використана / відхилена, причина**. Усі articleUrl, wikidataUrl, sectionUrl і searchUrl беріть з `summary.articleSources` / `analysis.articleSources`, не складайте самостійно. findings.sourceIds визначають джерела чисел. Для недоступної мови покажіть sitelinkPresent, searchCompleted/searchTruncated, реальні формулювання, пов’язаних кандидатів, причини й checkedAt. «Точного відповідника не знайдено серед перевірених кандидатів» не означає «статті немає».

Якщо старий run не має URL, виконайте `sources --run` із `mode: refresh` (лише метадані) або чесно позначеним `mode: historical` за недоступного live, потім report нового дочірнього run. Старий run не змінюйте й два роки переглядів заради посилань не перезавантажуйте. ARTICLE_SELECTION_CHANGED вимагає нового analyze/research; CONTENT_REVIEW_STALE — повторного прочитання змісту. Не видавайте перевірку метаданих за перевірку всієї аналітики.

Зупинка допустима за суттєвої неоднозначності, реального дозволу середовища, cooldown/бюджету чи відсутності придатних даних. Покажіть конкретний blocker і збережений run/checkpoint. Не обіцяйте відкладений запуск. Наявні придатні User-Agent та контакт не змінюйте й повторно не запитуйте. Якщо контакту ще немає, попросіть користувача надати свій email або URL зі способом зв’язку та поясніть, що він передаватиметься Wikimedia у User-Agent. Після усунення збою report використовуйте збережений runId.

Для зміни мов через research передайте `parentRunId` і новий analysis з **запитаними** мовами (не підміняйте їх попередніми supplementalLanguages). Код повторно використає знімки батька й кеш. Лише критерій — revise, лише мова PDF — report. Уже створений PDF повторно генерувати без причини не потрібно.

Компактний приклад для вже вибраної астрономії Q333 в uk/pl:

```bash
npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- research --input examples/research.json
```

Файл: `{"analysis":{"mode":"article","topics":[{"topicId":"astronomy","label":"Астрономія","concepts":[{"qid":"Q333"}]}],"languages":["uk","pl"],"queryLanguage":"uk","criterion":"yearOverYear"},"languagePolicy":"auto-supplement","report":{"locale":"uk"}}`. Для topic замініть analysis на `mode: topic`, topicPlanId, languages і потрібне джерело. API завжди перевіряє QID; перший пошуковий кандидат не вибирається автоматично. `demo:research` — синтетична перевірка пропусків/мов/PDF; `smoke:research` — живе інтервальне голодування pl/cs, без наперед заданої відсутньої статті.

## Вибір режиму й тематичний сценарій

«Покажи перегляди статті Хімія» → `article`: одна концепція на рядок, висновок лише про статтю. «Чи варто додати курс із хімії?» → `topic`: вибірка навчальних підтем; загальна стаття може бути окремим контрольним рядом. Не замінюйте широку тему однойменною статтею.

Якщо продуктовий контекст суттєво змінює склад (школа, університет, побут), поставте одне коротке уточнення. Не блокуйте кожен запит: без контексту запропонуйте базове охоплення та запишіть припущення. Для звичайної широкої теми орієнтир — 12–25 перевірених концепцій у кількох підтемах; це бюджет, не мінімум і не доказ репрезентативності.

1. Прочитайте [контракти](references/contracts.md) та [методологію](references/methodology.md). Зафіксуйте питання, контекст, мови, включні дати й межі. Перевірте релевантні офіційні [обмеження даних](references/api-sources.md): локальний реєстр не є повним каталогом усіх майбутніх інцидентів.
2. Запустіть `discover` з query, languages, seedQids/pageTitles за наявності, змістовними searchTerms, linkTitles і релевантними categoryTitles. Код перевіряє QID, aliases, sitelinks та канонічні сторінки. Пошук, посилання й категорії — тільки джерела кандидатів. Не називайте discovery повним; `discoveryTruncated` означає досягнення ліміту або неповну перевірку.
3. Прочитайте компактний summary; за потреби вибірково прочитайте discovery.json. Не передавайте собі всі денні ряди чи сотні кандидатів. Оберіть концепції за змістом **до перегляду їхньої динаміки**. Не додавайте масово речовини, біографії, компанії чи суміжні галузі. Не відбирайте за популярністю, знаком зміни або зручністю для висновку.
4. Створіть JSON для `plan`: питання, контекст, межі, підтематики, рішення selected/excluded з причиною, ролі root/core/extended, одна основна підтематика на концепцію, період, припущення й обмеження. Використовуйте тільки candidateId з discovery. `plan` створює незмінний topic-plan.json із compositionVersion. Кореневу статтю не додавайте вдруге до core.
5. Запустіть **один** `research` із вкладеним analysis (`mode: topic`, topicPlanId, languages, джерело) або analyze/report за потреби розгорнутого керування. Не запускайте кожну статтю вручну. Код збере спільний незмінний core та окремий extended. Покриття означає частку плану, не всієї тематики. Нові статті не приєднуються поступово до суми.
6. Прочитайте `inspect` і findings сторінками (`view: findings`, limit: 7, offset: nextOffset). Зіставте root/core/extended, абсолютну й нормалізовану зміни, рік і останні 3 місяці, внески компонентів, leave-one-out та симетричні сценарії календарних місяців. Критичні flags мають змінювати **головний висновок і відповідь агента**, а не залишатися приміткою.
7. Формулюйте спостереження в межах scope та періоду: падіння кореневої статті з різноспрямованими підтемами не є спадом усієї тематики; залежність знаку від одного компонента назвіть прямо; за неповного покриття скажіть, що даних недостатньо для узагальнення на план. Медіана й частка зростаючих концепцій описують залежну вибірку, не статистичний доказ. Не пояснюйте сплеск ботами, новинами або сезонністю без доказів. Перетин з інцидентом не доводить його впливу; глобальні коефіцієнти корекції заборонені.
8. Відокремте гіпотези продукту від фактів. Прив’яжіть пропозиції до конкретної підтеми й findingId: наприклад, прототип навчального завдання, перевірка прогалин знань, добровільна заявка на конкретний модуль або окрема перевірка оплати. Навіть стійке зростання не доводить готовності платити. Не додавайте Google Trends/SEO як приховану заміну джерела.
9. `report --run` створює **1–3 сторінки A4**. Коротке article може бути односторінковим; topic типово 2–3. Не обрізайте, не приховуйте переповнення й не додавайте порожні сторінки. Огляньте **всі** report-page-N.png, отримані з PDF, та назвіть згорнуті рядки/скорочення. Якщо огляд неможливий, скажіть це. Повертайте реальні runId, reportId, PDF із artifacts, ключові числа й застереження.
10. Зміна складу/мови/періоду topic потребує нового зафіксованого плану і `revise --run` із changes.topicPlanId; parentRunId зберігається. Зміна лише критерію чи перерахунок діагностики — revise без завантаження; мова PDF — report без мережі. `refresh` тільки явно; старі run незмінні. `replay` використовує знімки run; replayReportId — власні знімки звіту.

Для article: `resolve` → змістовний вибір реального QID → `analyze` з mode: article і topics → `inspect` → `report`. Перший результат пошуку не доводить відповідності; неоднозначність слід розв’язати. «Вивчення англійської» не підмінюйте «англійською мовою».

Готовий наскрізний **синтетичний** topic-сценарій: `npm --prefix "$WIKI_INTEREST_ROOT" run --silent demo:topic`. Він виконує discover → plan → analyze → report і навмисно демонструє падіння загальної статті та неоднорідні підтематики. Дані не описують реальну хімію. Для live приклад discovery — [discover-topic.json](examples/discover-topic.json); подальший вибір agent робить із фактичної відповіді.

## Компактний наскрізний приклад

Для запиту **«Досліди концепцію астрономії Q333 в українській Wikipedia; зроби PDF»** готові файли узгоджені. Q333 заданий у самому прикладі запиту, а API має його перевірити. Спочатку перевірте назву, опис і статтю з resolve; за невідповідності не продовжуйте.

```bash
npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- resolve --input examples/resolve-astronomy.json
npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- analyze --input examples/analyze.json
# Збережіть identifiers.runId із попереднього JSON у RUN_ID.
npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- inspect --run "$RUN_ID" --input examples/inspect-findings.json
npm --prefix "$WIKI_INTEREST_ROOT" run --silent cli -- report --run "$RUN_ID"
```

`examples/analyze.json`: `{"topics":[{"topicId":"astronomy","label":"Астрономія","concepts":[{"qid":"Q333"}]}],"languages":["uk"],"queryLanguage":"uk","criterion":"views"}`. Для довільної теми використовуйте пошук і власний обґрунтований вибір, а не цей QID. Для перевірки встановлення без Wikimedia: `npm --prefix "$WIKI_INTEREST_ROOT" run --silent demo:offline` — **синтетичні дані**, не дослідження реального інтересу.

## Стандартні значення й межі

- 24 останні завершені календарні місяці UTC. Явні дати включні й незмінні; назвіть фактичні межі.
- `access: all-access`, `agent: user`, `criterion: views`, `source: live`, `cachePolicy: reuse`; `queryLanguage` analyze — `uk`. Мови Wikipedia задаються явно.
- Ідентифікація Wikimedia спільна для HTTP, doctor, smoke й аудиту: явний WIKIMEDIA_USER_AGENT → наявний HttpOptions.userAgent → name/version та контакт із package.json. Публічний пакет контакту не містить. Для першого live-запиту отримайте погоджений контакт від користувача, якщо придатного налаштування ще немає. Передавайте повний заголовок через ENV; не змінюйте публічний package.json і не беріть email із git config. За потреби зберігайте значення в ігнорованому .env.local, а не в прикладах або журналах. Файл не читається програмою автоматично: завантажуйте його в тому самому shell, де викликаєте CLI; див. [налаштування](references/installation.md). Doctor показує джерело без значення. Порожній заголовок або placeholder — помилка. Offline/fixtures/report не потребують контакту; для них використовуйте doctor --offline.
- Критерії: `views`, `yearOverYear`, `relativeInterestChange`. Якість показується окремо. До 5 сумісних старих тем, до 30 концепцій у topic-плані, 10 мов. Discovery типово: 40 кандидатів, глибина 1, 160 логічних запитів; жорсткі межі 80/2/400, до 3 HTTP-спроб на запит.
- `offline` читає лише кеш Wikimedia; `fixtures` із `fixtureId: demo-v1` — тільки явно тестовий сценарій. Мережеві помилки не вмикають fixtures.
- На графіку до 4 серій; topic-таблиці показують ключові компоненти з кількістю згорнутих. Метрика охоплює весь оголошений придатний набір; суперечності залишаються в головному висновку. Кожен варіант має новий reportId.
- Перегляди не є людьми, аудиторією продукту, розміром ринку чи готовністю платити; мова Wikipedia не є країною. Причину сплеску без незалежного підтвердження не пояснюйте. Діагностика — евристика, не ймовірність; два роки не доводять сезонної моделі або прогнозу.

## Якщо виконання неповне

| Ситуація | Дія |
|---|---|
| Немає мовного розділу/статті або спільних концепцій | Завершіть доступні гілки через research з чинною мовною політикою; покажіть coverage й виключення. Не підміняйте тему чи мову та не називайте це нульовим інтересом. |
