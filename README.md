# wiki-interest

Навичка розташована в `wiki-interest/`. Встановлення, підключення до Codex / Claude Code та команди наведені в [README навички](wiki-interest/README.md).

## Логіка рішення та хід виконання

### Постановка задачі та межі

Навичка досліджує динаміку уваги до тем у мовних розділах Wikipedia, щоб сформувати гіпотези для подальшої продуктової перевірки. Перегляди статей не є пошуковими запитами або унікальними людьми; мовний розділ не визначає країну, а спостережуваний інтерес не доводить готовності платити. Тому результат — дослідницький звіт із джерелами, показниками та обмеженнями. Рішення про продукт потребує окремої перевірки проблеми, поведінки й оплати; автоматичного вердикту «запускайте продукт» тут немає.

### Архітектура та відповідальність

Codex або Claude Code забезпечує агента й локальне виконання. [SKILL.md](wiki-interest/SKILL.md) задає послідовність роботи та правила інтерпретації. Агент уточнює тему, читає статті й обґрунтовує вибір; [TypeScript CLI](wiki-interest/scripts/cli.ts) через [реєстр операцій](wiki-interest/src/operations/index.ts) перевіряє вхід, виконує розрахунки та створює артефакти. Файли дослідження зберігають підстави для перевірки й продовження.

Цей поділ використовує вже наявне агентне середовище, тому окремі AI-runner, LLM API, вебінтерфейс і сервер для роботи навички не потрібні. TypeScript об’єднує контракти, чисті функції розрахунків і генерацію результатів у Node.js; Zod додатково перевіряє JSON під час виконання. Це відповідність конкретній архітектурі, а не універсальна перевага мови.

Для недорогої моделі передбачено компактний JSON та порційне читання findings через `inspect`: денні ряди залишаються у файлах. Агенту не потрібно рахувати відсотки чи писати новий аналізатор. Економність і надійність такого підходу поки є архітектурним наміром, а не результатом модельного експерименту.

### Послідовність запиту

```text
Запит → тема й параметри → пошук та перевірка статей → фіксація плану
      → отримання даних → розрахунки й діагностика → висновки → графіки та PDF
```

Для конкретної статті достатньо `article`. Для питання про напрям продукту потрібний `topic`: загальна стаття не представляє всі підтематики. [Resolver](wiki-interest/src/resolver.ts) використовує Wikidata, мовні посилання й обмежений локальний пошук; перевіряє сторінку, перенаправлення та фактичний QID. Незавершений пошук не доводить відсутності відповідника.

Однаковий QID не гарантує однакового предмета статей. Агент читає збережений зміст, а [операція `review`](wiki-interest/src/source-operations.ts) фіксує рішення з цитатою та версією: `exact`, `broader`, `narrower`, `section_only`, `mention_only` або `ambiguous`. Ширша тема чи згадка не підміняють точний відповідник; неперевірений зміст залишається `pending`.

Для `topic` операції [`discover` і `plan`](wiki-interest/src/discovery.ts) зберігають кандидатів, межі, підтематики, включення й виключення до отримання переглядів. Це зменшує ризик відібрати лише зростаючі статті, хоча не доводить неупередженості агента. Дедуплікація за канонічною концепцією та фізичною сторінкою запобігає повторному підрахунку. Спільний `core` має однаковий склад між мовами й у часі; `extended` дає додатковий контекст лише всередині мови. Коренева стаття показується окремо.

[Операція `research`](wiki-interest/src/completion.ts) продовжує доступні гілки. `strict` залишає тільки запитані мови; стандартний `auto-supplement` може додати до двох мов тієї самої концепції з придатною історією, без відбору за зростанням.

**Ілюстрація, не проведений експеримент:** користувач порівнює тему українською та польською, але польський відповідник не підтверджено. За наявності українських даних код формує доступні показники й PDF. У `strict` додаткових мов немає; в `auto-supplement` можливі окремо позначені доповнення. Причина недоступності польської лишається видимою, початкове порівняння — неповним. Якщо придатних мов немає, зберігається причина зупинки, а не вигадані числа.

### Показники та стійкість

[Розрахунки](wiki-interest/src/calculations.ts) розділяють обсяг, середньодобовий рівень і динаміку. Річне вікно порівнює останні 12 повних місяців із попередніми 12; нещодавнє — останні три з тими самими місяцями попереднього року. Основні формули:

- зміна: `(поточна сума / попередня сума − 1) × 100%`;
- частка на мільйон: `сума переглядів теми / сума переглядів мовного розділу × 1 000 000`;
- внесок компонента: `(поточні перегляди компонента − попередні) / попередня сума core × 100` відсоткових пунктів.

Нормалізація використовує однакові дати й фільтри та відношення сум. Якщо весь розділ зростає швидше за тему, абсолютний обсяг може збільшитися, а частка — зменшитися. [Тематичний аналіз](wiki-interest/src/topic-analysis.ts) окремо показує core, extended, підтематики, напрям компонентів і їхні внески; відсотки статей не усереднюються замість зміни загальної суми.

Нульова база, нульовий знаменник і недостатня історія повертають `null` із причиною. Пропуски не стають нулями й не пересувають календарні вікна. [Recovery](wiki-interest/src/recovery.ts) розрізняє повні денні дані, придатні місячні API-агрегати та зміну на спільному піднаборі календарних днів. Для останньої застосовуються пороги покриття, спільна маска чисельників і знаменників та виключення 29 лютого. Такий показник не є повною річною зміною; місячні агрегати також не доводять повноти денних даних і не є незалежним джерелом.

[Сценарії чутливості](wiki-interest/src/sensitivity.ts) симетрично виключають однойменний місяць обох років; для topic додатково перевіряється вилучення кожної концепції. Початкові дані незмінні, сценарій не стає «виправленою правдою». Евристики не є статистичною ймовірністю. Неповний план переводить головний тематичний висновок у недостатність даних, а залежність напряму від статті явно змінює його формулювання.

### Повторні запити та звіти

[Кеш](wiki-interest/src/gateway.ts) повторно використовує відповідні знімки. Додавання мови потребує відсутніх блоків даних; для live-метаданих діє строк свіжості, тому нуль нових запитів не гарантується. Зміна лише критерію через [`revise`](wiki-interest/src/research.ts) використовує збережений dataset без збору; зміна мови `report` не змінює дані. Новий план створює нове дослідження зі зв’язком `parentRunId`.

Зберігаються джерела, статті, параметри запитів, знімки, контрольні суми, план, версії методології та показники. Findings містять шлях до метрики й посилання на докази. Повторення розрахунків за знімком відрізняється від `refresh`, який отримує потенційно змінені живі дані; змістовий вибір агента сам собою не детермінований.

[PDF на 1–3 сторінки](wiki-interest/src/reporting/report.ts) призначений для читання висновків, повні JSON/CSV — для перевірки. Скорочення позначаються. Посилання на конкретні статті дозволяють перевірити вибір джерел; поточна вебсторінка може відрізнятися від збереженої версії.

### Перевірки та використання AI

Реалізацію підтверджують код і різні рівні тестів: [відомі арифметичні результати](wiki-interest/tests/calculations.test.ts), [прогалини та резервні методи](wiki-interest/tests/recovery.test.ts), [HTTP-помилки](wiki-interest/tests/http.test.ts), [PDF і числа](wiki-interest/tests/report.test.ts), [джерела й посилання](wiki-interest/tests/sources.test.ts). Перевірка PDF програмою не замінює візуального огляду сторінок.

У [статусі за 27.09.2026](wiki-interest/references/implementation-status.md) задокументовано встановлення чистої копії, успішний `check` із 137 тестами та синтетичне PDF-демо. Це датований результат, не доказ live-дослідження. Живі CLI-smoke реалізовані, але повне проходження поточної версії не підтверджене. Окрема [оцінка реального агента на недорогій моделі](wiki-interest/references/evaluation.md) залишається `not_run`.

За [описом використання AI](wiki-interest/references/ai-usage.md), Codex допомагав писати код, документацію й тести; результати перевіряли розрахунками, регресіями та оглядом демонстраційних PDF. Це не незалежне модельне оцінювання.

### Компроміси та наступні кроки

Wikipedia неповно представляє теми; мовні статті відрізняються, API має обмеження, а перейменування можуть розривати історію. Доступна частина звіту зберігає користь без твердження про повне порівняння. Більший набір статей не гарантує репрезентативності ринку.

Є неузгодженість: [методологія](wiki-interest/references/methodology.md) описує core через повну історію, тоді як `buildTopicStudy` допускає також recovery-кандидатів із придатними місячними агрегатами або щонайменше 95% відомих днів. Це не гарантує обчислюваності всіх строгих метрик. Потрібно читати метод, покриття й попередження конкретного результату.

Розвиток варто вести ітераціями: складніший сценарій → вимірювання обмежень → локальна зміна → порівняння з попередньою версією. Запропоновані напрями, які ще потребують реалізації:

1. **Погоджений бот і вищі ліміти Wikimedia.** Запросити у відповідної wiki-спільноти статус схваленого бота (`bot flag`), додати автентифікацію його запитів і перевірити застосовні ліміти для використовуваних API. [Документація Wikimedia](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits) передбачає пільговий режим для автентифікованих ботів із цим статусом; операційні обмеження та вимоги `Retry-After` залишаються чинними. Це напрям для збільшення обсягів збору, який потребує погодження, а не вже отриманий доступ.
2. **Шаблони досліджень.** Додати повторно використовувані сценарії: порівняння мовних розділів, оцінка теми навчального курсу, перевірка стійкості зростання. Шаблон має задавати питання, параметри, правила відбору статей і структуру результату, залишаючи агенту перевірку змісту та адаптацію до конкретної теми. Розширювати набір шаблонів за результатами реальних сценаріїв.
3. **Обробка й представлення залежно від контексту.** Добирати візуалізацію до питання: лінійний графік для динаміки, стовпчикову діаграму для порівняння категорій або внесків, кругову — для невеликої кількості невід’ємних, взаємовиключних часток одного цілого. Для більших наборів додати групування й агреговані огляди, зберігаючи доступ до повних таблиць, джерел і застережень. Кожен новий формат перевіряти на відповідність вихідним числам і коректність порівняння.
